# Scaling-up benchmark

AccessMod 5 against accessmod-rs: facilities added one at a time where
they are most suitable and cover the most people. Results:
[`report.md`](report.md), generated by:

```sh
sh benchmark/scaling-up/run.sh
```

Needs Docker, the AccessMod 5 image `fredmoser/accessmod:5.9.2-beta.6` and
the oracle exports (`sh scripts/oracle/export.sh`). `REPEAT` (default 3)
sets the runs per measurement; the report gives the median. Scratch files
go to `_shared/benchmark/scaling-up/`.

## What is measured

**Demo project, full analysis.** The AccessMod 5 demo (227 × 196 cells,
10 existing facilities kept, exclusion 5 km around facilities, suitability
from population, distance to facilities and isotropic travel time from
roads, 10 facilities added, 120 min, anisotropic):

- AccessMod 5: the replay `scripts/oracle/scaling-up-demo.json` (from
  `replay/examples/demo_scaling_up`, with the image's demo population) run
  by `amAnalysisReplayExec`, each run in a fresh container. Loading
  `global.R` (median) is reported apart.
- accessmod-rs: `scaling-up run` on the same data
  ([`demo-job.json`](demo-job.json), also the job of
  `tests/oracle_scaling_up.rs`): capacity table, new facilities, residual
  population, catchments and reports.

There is no synthetic part: an engine-only lower bound would leave out
most of AccessMod 5's work here (suitability maps, buffers, rescales,
candidate evaluations), so only the full analysis is compared.

## How to read it

- Both produce the same facilities, cells and table
  (`docs/scaling-up.md`).
- Each iteration of AccessMod 5 runs several GRASS modules over the whole
  region (buffers, distance, moving window, rescales); accessmod-rs reads
  the grids once per iteration and searches from the best cells only.
